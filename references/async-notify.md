# 异步通知处理规范（共享）

本文档是盛付通所有异步通知（支付结果、退款结果、卡变更事件）的**通用处理规范**。各通知的具体参数请查阅对应的接口文档。

## 适用通知类型

| 通知类型 | 详细文档 | 重试 |
|----------|---------|------|
| 支付结果通知 | `references/payment-notify.md` | 是，指数退避 |
| 退款结果通知 | `references/refund-notify.md` | 是，指数退避 |
| 用户卡变更通知 | `references/card-notify.md` | **不重试** |

## 通用处理流程

```
1. 收到 POST 请求
2. 【验签】用盛付通公钥验证 sign → 不通过则丢弃（详见下方）
3. 【检查】returnCode=SUCCESS 且 resultCode=SUCCESS
4. 【幂等】按业务的唯一键去重：
    - 支付通知 → transactionId
    - 退款通知 → refundId
    - 卡变更通知 → agreementNo + eventType
   已处理则直接返回 SUCCESS
5. 【查单确认】（推荐）主动调用查询接口二次确认状态
    - 支付 → 订单查询
    - 退款 → 退款查询
    - 卡变更 → 查询签约关系接口
6. 【业务处理】更新状态、发货/恢复库存/记录卡绑定
7. 【返回】纯文本字符串 "SUCCESS"
```

## 验签规则（所有通知通用）

1. 取出通知中的 `sign` 字段
2. 将**除 sign 外的所有字段**按 key 字典序（ASCII）排序
3. 拼接为 `key1=value1&key2=value2&...`，空值不参与
4. 使用**盛付通公钥**验签，算法与 `signType` 对应
5. 验签不通过 → 丢弃该通知，记录告警日志

## 返回格式（极其重要）

**返回纯文本字符串 `SUCCESS`**（区分大小写）。

- ❌ `{"code":0,"msg":"success"}` — JSON
- ❌ `success` — 小写
- ❌ `OK`
- ✅ `SUCCESS`

不返回或返回非 `SUCCESS` 会触发重试（对支持重试的通知类型）。

## 幂等处理

盛付通可能因重试导致同一通知发送多次。建议方案：

1. **数据库唯一索引**：`UNIQUE(transactionId)` / `UNIQUE(refundId)` / `UNIQUE(agreementNo, eventType)`
2. 或 **Redis 去重**：`SETNX notify:{refundId} 1 EX 86400`

## 安全建议

1. **必须验签**：绝对不能跳过，这是防止伪造回调的安全底线
2. **主动查询兜底**：即使实现了回调，也建议保留定时主动查询
3. **日志记录**：完整记录所有通知的原始 body 和处理结果，便于问题排查
4. **异步处理**：耗时业务操作应异步化，通知接口 5 秒内返回
5. **状态保护**：只有当前状态为"待处理"时才更新为"已完成"，防止状态回退

## 排查通知收不到

1. 确认 `notifyUrl` 是公网可访问的（生产必须 HTTPS）
2. 确认回调接口返回纯文本 `SUCCESS`（不是 JSON）
3. 检查服务器防火墙/WAF 是否拦截了盛付通 IP
4. 用主动查询接口作为兜底方案
